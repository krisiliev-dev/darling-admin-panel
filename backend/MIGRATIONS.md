# admin.db migrations (Alembic)

The panel's `admin.db` (users, audit, staging tables) is defined by the SQLAlchemy models in
`app/models.py`. **Alembic** is the migration tool for real schema changes.

## Runtime is unchanged
At startup the app still runs `db.create_db_and_tables()` (create_all + `_backfill_columns`), which
handles fresh DBs and **additive** column adds. Alembic is for what that can't do — **renames, drops,
type changes, data migrations**. Adopt it the first time you need one of those.

## Make a change
```bash
cd backend
# 1. edit app/models.py
# 2. generate a migration from the model diff
alembic revision --autogenerate -m "short description"
# 3. review the generated file in migrations/versions/ (autogenerate is a draft, not gospel —
#    check column types, server_defaults, and any data backfill it can't infer)
# 4. apply it
alembic upgrade head
```

## Adopt on an existing DB (one time)
An `admin.db` created by `create_all` already has the baseline schema, so **stamp** it as current
instead of re-running the baseline:
```bash
alembic stamp head
```

## Notes
- `migrations/env.py` reads the DB URL from `Settings.admin_db_url` (strips `+aiosqlite` → sync driver
  for migrations) and uses `render_as_batch=True`, so SQLite ALTERs (drop/rename/retype) work via
  copy-and-move table rebuilds.
- `0001` baseline (`*_baseline_schema.py`) captures the current schema.
- Migrations are excluded from ruff (autogenerated).
- Eventually, replace the startup `_backfill_columns` with `alembic upgrade head` in the deploy so the
  DB schema has a single source of truth; until then the two coexist safely (both additive-compatible).
